# DrawingScene 1.2

`DrawingScene` is the portable 2D contract for NaturalCAD. The Hugging Face prototype proves the contract first; the main app will later use the same scene for its 2D workspace.

## Boundary

The scene contains only validated drawing intent:

- schema version and coordinate system
- drawing title and units
- layers
- typed entities with stable IDs
- drafting-standard profile plus CAD-style by-layer display color, plot color, linetype, and lineweight

Prompts, uploaded images, model routing, usage, run IDs, logs, and storage metadata stay outside the scene.

## Supported entities

- polylines
- circles
- arcs
- obround slots
- polygon hatches with inner holes, named patterns, scale, angle, and SVG-preview opacity
- text
- linear dimensions
- leaders

Every entity has a stable `id`. A refinement returns the complete updated scene and preserves IDs for unchanged geometry. This gives the future main app a clean basis for version diffs and feature-level editing.

## Deterministic pipeline

```text
prompt / image / prior scene
        ↓
model JSON response
        ↓
DrawingScene validation + normalization
        ↓
shared scene ──→ SVG preview
             └─→ DXF export
```

The SVG and DXF paths never consume raw model output directly.

## Validation rules

- known units only: `mm`, `cm`, `m`, `in`, `ft`
- finite numeric coordinates
- bounded entity and point counts that reject overflow rather than silently truncating
- positive radii and widths
- slot length must be at least its width
- allowlisted linetypes and hatch patterns
- normalized layer names
- every entity assigned to a defined layer
- at least one supported geometry entity

## CAD standards and display hierarchy

Every entity carries a semantic layer name. DrawingScene 1.2 adds `standard_profile`; the HF generator uses `NOAH_URIU_2D_V1`, derived from Noah's URIU Rhino layer template. The profile resolves exact nested layer paths, semantic roles, working/display RGB, black plot RGB, linetype, linetype scale, plot visibility, and exact millimeter lineweight without asking the model to invent styling.

The standard includes plan, electrical, section/elevation, detail, annotation, and helper branches. Legacy scenes remain valid through the generic profile; legacy names such as `OUTLINE`, `DETAIL`, `HATCH`, and `DIMENSIONS` are mapped to standard leaves when a URIU scene is requested.

The scene budget supports 128 polylines, 128 points per entity, and 64 hatch regions, with explicit total entity and point limits.

DXF does not support Rhino's `::` hierarchy separator, so export flattens it to `$` while preserving the original path, parent, semantic role, plot color, and exact lineweight in `NATURALCAD` XDATA. DXF entities remain BYLAYER, standard RGB is stored as true color, and exact profile widths are snapped only where DXF's lineweight enum requires it (for example 0.075 mm -> 0.09 mm).

Patterned SVG hatches are generated by the same `ezdxf` pattern definitions and nested boundary rules as DXF, including holes, scale, angle, and deterministic origin. Preview rendering is capped at 4,000 segments per hatch and 16,000 per scene; capped previews are marked `data-preview-simplified="true"` while the exported DXF retains the full hatch definition. `opacity` remains preview-only so DXF hatches stay broadly compatible.

The default in-app view uses colored CAD working layers. `render_svg(..., plot_mode=True)` switches to black plot colors on white and omits non-plot construction/helper layers.

## Prototype artifacts

Each completed run writes:

- `<run_id>.scene.json` — portable DrawingScene
- `<run_id>.svg` — browser preview
- `<run_id>.dxf` — QCAD-compatible exchange file

## Main-app merge seam

The current backend already supports projects with `mode="sketch"` and `output_type="2d_vector"`. The merge should add a real 2D worker dispatch rather than reuse the existing worker path that extrudes a thin 3D solid.

The web app should keep one project/conversation shell and route the workspace by output type:

- `2d_vector` -> DrawingScene + 2D drafting viewport + DXF/SVG/JSON exports
- `3d_solid` -> current 3D spec + GLB viewport + STEP/STL/GLB exports

Keep 2D and 3D project histories separate even though they share the application shell.
